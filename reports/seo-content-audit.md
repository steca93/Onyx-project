# SEO content audit — live catalog, per locale

Sources: **sr** is read live from WPGraphQL (read-only). **en/de** come from the storefront's translation overlay (`src/i18n/catalog/{en,de}.json`); WordPress has no multilingual plugin.

Generated by `npm run seo:audit`. **32 products, 11 categories, 287 issues.** [`seo-content-audit.csv`](seo-content-audit.csv) has one row per issue per item per locale, where `locale` is `sr`, `en`, `de`, or `all` for locale-independent issues like images, price and SKU. Proposed copy for all three languages is in [`seo-suggestions.csv`](seo-suggestions.csv), and terminology in [`src/i18n/glossary.md`](../src/i18n/glossary.md). Nothing was written to WordPress.

How staleness is tracked:
- Each translation records the WooCommerce `modified` date of the Serbian source it was made from (`sourceModified`, set by `npm run i18n:stamp`).
- The audit flags any product whose Serbian source has been edited since. After updating such a translation, run `npm run i18n:stamp <slug>`.
- **Categories can't be tracked**: WPGraphQL exposes no `modified` date for them.

Locale-specific findings:
- **The internal "NAPOMENA" note** on the red Hex pad was carried into the English ("NOTE:") and German ("HINWEIS:") descriptions too. Remove it in all three languages.
- **No categories have an intro text** in en/de either. Drafts are in the suggestions CSV.
- **Names too long for titles:** 14 in en, 16 in de, 19 in sr. The storefront clamps them; the CSV proposes shorter SEO titles.

## Fix first (high impact)
1. **11 placeholder products are published.** Their names and slugs are the same as a category's (`/proizvod/poliranje`, `/proizvod/ppf-auto-folija`, …). They have no image, no price, only "Uncategorized", and one line of text. They're live pages, in the sitemap, and show up in "newest"/search listings as unpriced items. **Recommendation:** unpublish or delete them in WooCommerce (Products → filter by *Uncategorized*). The mu-plugin will refresh the storefront automatically.
2. **Internal note visible to customers:** the description of the red Hex finishing pad (`hex-sundjer-za-finis-poliranje-onyx-evolution-130mm-crveni-finishing`) ends with "NAPOMENA: …", a note about the short description having been copied from the Hot Wheel product.
3. **Copy-paste content:** the Fish Scale towel's descriptions are the Glass Wipe product's text (it even calls itself "Glass Wipe"). This is duplicate content, and wrong for customers.
4. **All 11 categories have no description and no image.** Category pages are bare product grids with no indexable text, and share cards fall back to the default OG image. `seo-suggestions.csv` has a proposed intro for each.

## Where should per-product, per-locale SEO fields live long-term?

Constraint: EN/DE content does **not** live in WordPress. It lives in the storefront repo, so any WordPress-side SEO field would only cover Serbian unless translations also move to WordPress.

**Recommendation: keep templates + native fields for Serbian (WooCommerce short description and alt text) and the overlay for EN/DE. When dedicated SEO titles are needed, add optional `seoTitle` / `seoDescription` per locale to the overlay files, with Serbian taken from two lightweight custom fields (Option C).** Move to a WordPress multilingual plugin only if non-developers need to edit EN/DE content themselves.

### Option A: templates + native fields + overlay (built now)
- ✅ Zero backend weight; one source of truth per language; already works in all three languages.
- ✅ The audit catches missing, stale and leftover-Serbian translations.
- ❌ No separate SEO title; long names are clamped.
- ❌ EN/DE edits need a developer and a deploy.

### Option B: Polylang/WPML + WPGraphQL extension + Yoast/Rank Math
- ✅ Editors manage all three languages and their SEO fields in wp-admin, with per-language slugs.
- ❌ **Heaviest backend:** a multilingual plugin (duplicate posts per language, extra queries), an SEO plugin (indexables, cron, its own sitemaps and schema that the headless site doesn't use), plus their WPGraphQL add-ons. That means bigger payloads and more PHP on a backend already at ~0.6 s per query.
- ❌ It means migrating the overlay into WordPress and rewriting the data layer to query by language.
- ❌ Yoast/Rank Math support for WPML/Polylang is uneven, especially through WPGraphQL.

### Option C: small custom fields (middle ground)
- A ~40-line mu-plugin registers `_onyx_seo_title` / `_onyx_seo_description` on products, fetched only by the product page query. That covers Serbian.
- EN/DE get matching optional `seoTitle` / `seoDescription` keys in the overlay.
- The storefront uses them when set and falls back to templates otherwise.
- Almost no backend cost; I can write it into `wp-backend/` on request.
